# Technical Reference

This document covers the build system, architecture, and technical conventions for TableTogether. For product/UX philosophy, see the project's CLAUDE.md (local-only).

## Build System

The iOS/iPadOS/Mac Catalyst app uses **Swift Package Manager** for source management and **XcodeGen** for the thin Xcode project wrapper. The tvOS app uses a separate xcodeproj generated by `regenerate_tvos_project.py`.

### Build Commands

**iOS / iPadOS:**
```bash
xcodegen generate --spec project.yml
xcodebuild build -project TableTogether.xcodeproj -scheme TableTogether \
  -destination 'generic/platform=iOS Simulator' \
  -configuration Debug CODE_SIGNING_ALLOWED=NO
```

**Mac Catalyst:**
```bash
xcodebuild build -project TableTogether.xcodeproj -scheme TableTogether \
  -destination 'platform=macOS,variant=Mac Catalyst' \
  -configuration Debug CODE_SIGNING_ALLOWED=NO
```

**tvOS:**
```bash
python3 regenerate_tvos_project.py
xcodebuild build -project TableTogetherTV/TableTogetherTV.xcodeproj -scheme TableTogetherTV \
  -destination 'generic/platform=tvOS Simulator' \
  -configuration Debug CODE_SIGNING_ALLOWED=NO
```

**Preflight (run before pushing):**
```bash
scripts/preflight.sh           # Full validation
scripts/preflight.sh --quick   # Skip builds
```

## Architecture

### Core Data + CloudKit (Dual Store)

The app uses `NSPersistentCloudKitContainer` with **two stores**:

1. **`private.sqlite`** — Owner's data. Syncs to the user's CloudKit private database. All locally-created records live here.
2. **`shared.sqlite`** — Data shared **BY OTHER USERS** with this device. Only populated when this user accepts an invitation from someone else.

**Critical:** Both stores use the **default Core Data configuration** (no named configurations). This matches Apple's CoreDataCloudKitShare sample. Named configurations with identical entity lists break Core Data's store routing.

### Sharing Model

When the household owner taps "Invite Family Member":
1. `container.share([household], to: nil)` creates a CKShare for the household
2. The **object graph stays in the owner's private store** but moves to a new shared zone within the owner's private CloudKit database
3. The CKShare is presented via `NSItemProvider.registerCKShare` + `UIActivityViewController`
4. When a participant accepts via the share link, their device's **shared store** receives the data via `acceptShareInvitations(from:into:sharedPersistentStore)`

CKShare participant identity is **only revealed after acceptance**. The `PendingInvitationStore` allows the owner to label pending invites locally so the household list shows a meaningful name in the meantime.

### Deterministic IDs

System-created entities use **deterministic UUIDs** so multiple devices converge on the same record without coordination. Without this, each device creates its own random-UUID copy on first launch before CloudKit sync completes, leading to duplicates that cannot be merged.

| Entity | ID Source |
|--------|-----------|
| `Household` | Well-known UUID `Household.defaultID` |
| `User` (default "Me") | Well-known UUID `User.defaultMeID` |
| `MealArchetype` (system) | SHA-256 of `"archetype:{rawValue}"` via `UUID.deterministic(from:)` |
| `WeekPlan` | SHA-256 of normalized week start date |
| `MealSlot` | SHA-256 of `"mealslot:{date}:{day}:{mealType}"` |
| `Recipe`, `Ingredient`, etc. (user-created) | Random `UUID()` |

Helper: `UUID.deterministic(from: String)` in `Sources/Extensions/UUID+Deterministic.swift`.

## Naming Conventions

- **Views:** `*View.swift` (e.g. `RecipeLibraryView.swift`)
- **Components:** `*Components.swift` (extracted subviews from large view files)
- **Services:** `*Service.swift` or `*Manager.swift`
- **Core Data models:** Singular nouns (`Recipe`, `Household`)
- **Core Data file naming:** `Entity+CoreData.swift`

## Data Flow in Views

| Wrapper | Use For | Example |
|---------|---------|---------|
| `@Query` | SwiftData reads with optional `#Predicate` filter | `@Query(filter: ...)` |
| `@FetchRequest` | Core Data reads (most of this app) | `@FetchRequest(sortDescriptors: ...)` |
| `@Environment` | Injected services and system values | `@Environment(\.managedObjectContext)` |
| `@ObservedObject` | Two-way binding to a Core Data `NSManagedObject` | `@ObservedObject var recipe: Recipe` |
| `@State` | Local UI state only | `@State private var showingDetail = false` |

**Never** use `@State` for model data.

### Core Data exception to the "no `@ObservedObject`" rule

The general convention (used across the author's other projects) is *never* use
`@ObservedObject` — bind to models with `@Bindable`. That rule assumes SwiftData `@Model`
types, which conform to the `Observable` macro. **This app uses Core Data, so it does not
apply.** `NSManagedObject` subclasses (`Recipe`, `Ingredient`, `MealSlot`, …) conform to
`ObservableObject`, not `Observable`, so `@Bindable` does not compile against them.
`@ObservedObject` is the correct — and only — idiom for two-way binding to a managed object
here. Use `@Environment` to inject the `@Observable` services (e.g. `PersistenceController`),
and `@ObservedObject` to observe a managed object passed into a row/detail view.

## Concurrency

- **async/await only** — no Combine, no callback-based APIs (except where bridging Apple APIs that haven't been async-ified)
- `@MainActor` for view models and services that touch UI/Core Data viewContext
- Core Data background contexts for heavy work
- `nonisolated` for `@objc` notification observers that fire on background queues

## Logging

`AppLogger` provides categorised `os.Logger` instances:
- `AppLogger.cloudKit` — CloudKit operations
- `AppLogger.swiftData` — Persistence (save, fetch, history)
- `AppLogger.app` — Lifecycle events
- `AppLogger.sharing` — Sharing operations
- `AppLogger.sync` — CloudKit mirroring events
- `AppLogger.parser` — Recipe parsing
- `AppLogger.network`, `AppLogger.nutrition`, `AppLogger.scanner`, `AppLogger.grocery`, `AppLogger.insights`, `AppLogger.ui`

**Never use `print()` in production code.**

## Testing

Uses Swift Testing framework (`import Testing`, not XCTest):
```swift
struct MyServiceTests {
    @Test func descriptiveBehaviourName() {
        let service = MyService()
        #expect(service.result == .expected)
    }
}
```

## CI Pipeline

Defined in `.github/workflows/ios.yml`. The `validate` job runs on every push:
1. Install XcodeGen and SwiftLint
2. Run SwiftLint (errors fail the build, warnings allowed)
3. Generate iOS xcodeproj from `project.yml`
4. Validate `MARKETING_VERSION` consistency
5. Validate App Store metadata character limits
6. Build iOS Simulator, Mac Catalyst, and tvOS Simulator
7. On main branch: deploy iOS and tvOS to TestFlight via fastlane

## CloudKit Diagnostics

Built-in diagnostics view in Settings shows:
- iCloud account status, container ID
- Private/Shared store load status
- Recent mirroring events with success/error
- Record counts per entity
- Recovery actions: Reset Shared Store, Reset All Sync Data, Copy Diagnostics
